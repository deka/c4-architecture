<p class="lead">C4 is a way to describe software architecture as a set of maps at different zoom levels, created by Simon Brown. This page is a short introduction; the reference is <a href="https://c4model.com/">c4model.com</a>.</p>

Most architecture diagrams are boxes and arrows with no agreed meaning: is that box a server, a library, a team? C4 fixes this with **a small set of abstractions** and **one diagram per zoom level**. Like Google Maps, you zoom in only where it helps.

## Abstractions

| Level | Abstraction | What it is | Examples |
|---|---|---|---|
| 1 | **Person** | A human user or role, not an individual. | Customer, Back-office agent |
| 1 | **Software system** | Something that delivers value to people, owned by one team or organisation. | Your product, a payment provider, an ERP |
| 2 | **Container** | A separately deployable or runnable unit that executes code or stores data. *Not* a Docker container in the strict sense. | Web app, mobile app, API, worker, database, queue |
| 3 | **Component** | A grouping of related functionality behind an interface, inside one container. | Module, package, service class |
| 4 | Code | Classes, functions, tables. | Usually generated by your IDE: not supported here. |

Each element has a **name**, a short **description** of its responsibility and, for containers and components, a **technology**. **Relationships** link elements with a verb phrase ("Places orders using") and, between containers, a protocol ("HTTPS/JSON").

## Notation used here

C4 is notation independent. This runtime draws:

- **Blue** for what belongs to the systems you model, a little lighter at each level down (person, system, container, component);
- **Grey** for elements marked `external`: owned by someone else;
- a **dashed frame** for the boundary of the system or container being zoomed into, and for [groups](/views/#groups);
- the element type and technology under the name, in brackets: `[Container: Go]`;
- relationship labels with the description, then the technology in brackets;
- a legend under each diagram.

The colour belongs to the element, not to the view: an element looks the same in every diagram. [Tags and styles](/styles/) change it on purpose.

## Modelling tips

- **System or container?** If another team owns it, or users see it as a product of its own, it is a software system. If it is deployed as part of what you design, it is a container.
- **Data stores are containers** of the system that owns them, not systems. Tag them `Database` and give the tag a `cylinder` shape.
- **Queues and topics** are containers too (`pipe` shape). Draw publish and consume relationships through them.
- **Relationship direction** follows the initiator: the caller points to the callee; a consumer points to the topic it reads from.
- **Declare relationships at the most detailed level** you model. Links between parents are [derived automatically](/views/#implied-relationships).
- **Keep views small.** Past ~20 elements, split the view or exclude elements; `inspect` warns about it.

### Anti-patterns

- Mixing levels in one view (a component next to systems).
- A database or Kafka modelled as a software system.
- Forgetting external systems: identity provider, payment, email, monitoring.
- Vague relationships ("Uses", "Calls") or no description at all.
- Going down to components before the containers are agreed.
